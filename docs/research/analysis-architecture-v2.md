# Story Guard 분석 아키텍처 개선안

## 현재 구현되어 있는 보호 장치

- 원고 임포트 시 프로젝트별 인덱스 작업을 디바운스해 여러 파일을 한 번에 색인한다.
- EmbeddingGemma는 별도 프로세스에서 실행하고, 배치 단위 진행률과 메모리 오류 시 배치 축소를 사용한다.
- GPT 검토는 작은 창으로 나누며 각 창의 체크포인트와 시도 횟수를 SQLite에 저장한다.
- 실패한 창은 격리하고 완료된 창의 결과는 보존한다. 이후 같은 요청은 완료된 창을 재사용한다.
- 문서 내용 해시와 임베딩 인덱스 서명을 비교해 변경되지 않은 회차를 재사용한다.

## 다음에 구현할 구조

### 1. 영속 작업 큐

분석 요청을 HTTP 요청의 수명과 분리한다. `analysis_jobs`가 작업 상태의 단일 원천이 되며, 앱 시작 시 `running` 작업을 중단 상태로 닫고 체크포인트가 남은 창을 재시도 대상으로 표시한다.

```text
queued → indexing → reviewing → merging → completed
                         └──────→ partial / retryable
```

### 2. 자원 예산 관리자

시작 시 CPU 코어, 사용 가능 메모리, GPU 지원 여부를 측정해 임베딩 배치와 동시 GPT 창 수를 정한다. 메모리 압박이 감지되면 배치를 줄이고 진행률에 상태를 남긴다. 임의의 반정밀도 전환은 CPU에서 벡터 오류를 만들 수 있으므로 기기별 검증 뒤에만 허용한다.

### 3. 모델 수명 관리

색인과 검토 사이에는 임베딩 워커를 유지하되, 분석이 끝나거나 취소되면 `release()`를 호출한다. 장시간 유휴 상태에서는 다음 요청 전에 워커를 재생성한다. 이를 통해 모델 파일 크기와 실행 중 RSS를 구분해 관리한다.

### 4. 영향 범위 재분석

회차가 수정되면 수정 회차의 청크만 다시 임베딩한다. GPT 검토는 수정 회차와 관계된 창만 다시 실행하고, 영향을 받는 관계·이슈만 병합한다. 근거 청크가 삭제된 결과는 자동으로 확정 상태에서 후보 상태로 내린다.

### 5. 제공자 회로 차단기

연속 provider 오류가 발생하면 전체 작업을 실패시키지 않고 창을 격리한다. 일정 시간 후 자동 재시도하지 않고 사용자가 실패 창만 재시도할 수 있게 하며, 인증 오류·동의 취소·원고 변경은 즉시 사용자 조치 상태로 분류한다.

## 검증 기준

- 새 원고 10편과 기존 원고에 1편 추가하는 시나리오를 각각 실행한다.
- 회차 1편 수정 후 재임베딩 청크 수와 GPT 재요청 창 수를 기록한다.
- GPT 지연·네트워크 오류를 주입해 성공 창 보존, 실패 창 격리, 재시도 병합을 확인한다.
- 10·20·50편에서 총 시간, p95 창 시간, 최대 RSS, 실패율을 측정한다.
- 모델 변경 비교는 동일 청크와 동일 질의를 사용하고 검색 상위 결과 일치율을 포함한다.

현재 브랜치에는 런타임 분리, 모델 배치 축소, 임베딩 워커 해제가 적용되어 있다. 다음 코드 작업은 영속 큐 자체보다 먼저 앱 재시작 후 `partial` 작업을 다시 선택해 재개하는 API와 UI를 연결하는 것이다.
