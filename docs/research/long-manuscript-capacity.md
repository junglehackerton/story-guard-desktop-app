# 장편 원고 처리 용량 기준

이 문서는 Story Guard의 장편 원고 지원 범위를 설명하기 위한 기준이다. 로컬 청킹·체크포인트 실행 시간과 실제 GPT 제공자 응답 시간은 서로 다른 변수이므로 하나의 성능 수치로 합치지 않는다.

## 원고 크기 구간

| 구간 | 예시 | 원고 문자 수 | 목적 |
|---|---|---:|---|
| 소규모 | 10회 × 6,200자 | 약 62,000자 | 첫 분석·시연 기준 |
| 장편 | 100회 × 6,200자 | 약 620,000자 | 대량 등록·증분 분석 기준 |
| 긴 회차 | 10회 × 20,000자 | 약 200,000자 | 회차가 긴 원고의 스트레스 기준 |
| 웹소설 유사 스트레스 | 10회 × 50,000자 | 약 500,000자 | 긴 회차·초기 일괄 등록 검증 |

한국어 웹소설의 실제 회차 길이와 편수는 작품·플랫폼마다 다르다. 따라서 위 숫자를 업계 평균이나 지원 상한으로 홍보하지 않고, 재현 가능한 테스트 구간으로만 사용한다.

현실적인 부하 기준을 정할 때는 회차당 약 5,000자를 참고값으로 둔다. 국내 연재 안내와 작가 사례에서 5,000자 안팎을 흔한 회차 분량으로 설명하지만, 이는 작품·플랫폼별 편차가 큰 경험적 기준이다 ([PYOZI 분량 가이드](https://pyozi.com/blog/word-count-guide), [문피아 작가 사례](https://www.munpia.com/novel/detail/584706), [예스24 집필 안내](https://m.yes24.com/goods/detail/124991030)). 따라서 부하 테스트는 5,000자 회차와 20,000자 이상 긴 회차를 모두 포함하고, 제품에서는 문자 수와 예상 검토 구간을 함께 보여준다.

## 현재 처리 규칙

- 파서 청크는 검색을 위해 작게 유지한다.
- GPT 검토는 한 회차 안에서 최대 5,200자 또는 12개 청크를 하나의 검토 구간으로 묶는다.
- 완료된 검토 구간은 원문·모델·추론 강도·스키마·설정의 fingerprint가 같을 때 재사용한다.
- 새 회차를 추가하면 새 회차 구간만 요청하고, 기존 검증 구간은 재사용한다.
- 회차를 교체하면 변경된 fingerprint의 구간만 다시 요청한다.
- 한 구간의 시간 초과·응답 형식 오류는 해당 구간에 격리하고 나머지 구간을 계속 처리한다. 재실행 시 성공 구간은 반복하지 않는다.

## 검증 결과

### 62,000자 기준

- 10회·162 검색 청크·20 GPT 검토 구간
- 정상 빈 JSON provider stub 기준 오케스트레이션 0.15초
- 실제 EmbeddingGemma FP32 색인: 17.54초, 평균 질의 0.129초(2026-09-13 재실행; 모델 워커 warmup 5.90초 별도)
- 같은 원고에서 11회차 추가 시 새 GPT 검토 구간 5개만 요청하고 20개를 재사용했으며, 1회차 본문 교체 시 1개 구간만 요청하고 23개를 재사용했다.
- 임베딩 측정에는 실제 GPT 요청과 판정 품질이 포함되지 않는다.

### 200,000자 기준

- 10회·495 검색 청크·55 GPT 검토 구간
- timeout 1회를 주입해도 구간 분할·재시도로 최종 실패 0
- 11회차(20,000자)를 추가한 재분석: 신규 요청 5개, 기존 구간 51개 재사용

### 100,000자 기준

- 10회·회차당 10,000자·230 검색 청크
- 실제 EmbeddingGemma 300M 색인 33.28초(초당 6.91청크)
- 이 측정은 해당 Mac의 로컬 CPU 실행이며 모델 워커 로딩과 실제 GPT 검토 요청·응답 시간은 포함하지 않는다.
- 같은 10회라도 회차당 글자 수에 따라 최초 준비 시간이 달라지므로, 앱은 편수와 함께 문자 수·청크 수·예상 구간을 표시해야 한다.
- 실제 Gemma 색인과 GPT 오케스트레이터를 연결한 로컬 통합 실행은 240청크·provider stub 30회·42.8초에 실패 없이 완료됐다. 외부 GPT 응답·품질은 포함하지 않으며, 로컬 검색과 체크포인트 경로가 함께 동작하는지 확인한 수치다.

### 500,000자 기준

- 10회·1,243 검색 청크·121 GPT 검토 구간
- 첫 구간 timeout 1회를 자동 분할해 최종 실패 0으로 완료
- 11회차(50,000자)를 추가한 재분석: 신규 요청 11개, 기존 구간 111개 재사용
- provider stub 기준 오케스트레이션 1.067초이며 실제 GPT·임베딩 시간은 포함하지 않는다.

### 620,000자 기준

- 100회·1,500 검색 청크·200 GPT 검토 구간
- provider stub으로 200개 구간을 끝까지 처리하고 실패 0
- 실제 제공자 응답을 구간당 15초·30초·60초로 가정하면 직렬 요청 시간은 각각 약 50분·100분·200분이다.
- 이 시간은 산술 투영이며 실제 GPT 속도, 네트워크, 계정 한도, 모델 품질을 측정한 결과가 아니다.

### 1,860,000자 기준

- 300회·4,500 검색 청크·600 GPT 검토 구간
- provider stub 기준 600개 구간을 15.081초에 오케스트레이션하고 실패 0으로 완료했다.
- 직렬 GPT 응답을 15초·30초·60초로 가정하면 약 150분·300분·600분이다.
- 이 규모에서는 작품 전체 분석을 한 번에 실행하지 말고, 회차 범위 또는 변경분 단위로 나누는 UX가 필수다.

### 회차당 100,000자 스트레스 기준

- 10회·총 1,000,000자에서 2,475 검색 청크·231 GPT 검토 구간이 생성됐다.
- provider stub에서 timeout 1회를 주입해도 2.785초에 실패 0·`completed`로 끝났고, 11회차 추가 시 신규 21구간만 요청하고 기존 211구간을 재사용했다.
- 구간당 15~60초라는 현재 안내 범위를 적용하면 GPT 직렬 검토는 약 58~231분으로 계산된다. 이는 네트워크·계정·모델에 따라 크게 달라지는 계획용 범위이며 실제 보장 시간이 아니다.
- 이 수치는 청킹·체크포인트·증분 오케스트레이션 검증이다. 실제 Gemma 색인과 GPT 응답 지연·품질은 별도 수치로 관리한다.

실제 EmbeddingGemma-300M 워커로 같은 10회·회차당 100,000자(총 1,000,000자)를 색인한 결과는 2,240청크·304.220초(약 5분 4초, 초당 7.363청크)였다. 격리 워커를 포함한 최대 RSS는 1,659.0MB였고, 11회차를 추가할 때는 신규 224청크만 30.366초에 처리하고 기존 벡터를 재사용했다. 이는 해당 Mac의 로컬 CPU·메모리 측정이며 GPT 응답 시간·분석 품질은 포함하지 않는다. 기기 메모리가 제한된 경우 Gemma를 무조건 선택하지 않고 Qwen 또는 회차 범위 분할을 안내해야 한다. 원본 결과는 `output/validation/realistic-manuscript-20260912/gemma-long-index.json`에 보존한다.

## 제품 동작 기준

1. 분석 시작 전에 `/projects/{id}/analysis/estimate`로 실제 문서 수·문자 수·청크 수·검토 구간 수를 보여준다.
   20개 이하 청크도 분석기가 실제로 요청하는 청크 수를 그대로 표시한다. 예를 들어 10회·10청크는 10개 검토 구간으로 계산한다.
2. 첫 장편 분석은 예상 구간 수와 사용자 계정의 요청량을 고지한다.
3. 작업 중에는 완료·진행·실패·재시도 필요 구간을 구분한다.
4. 앱을 닫거나 네트워크가 끊겨도 완료된 구간과 기존 게시 결과는 보존한다.
5. 사용자는 실패한 구간만 재시도할 수 있고, 재시도할 때 모델·추론 강도·원문 변경 여부를 확인한다.

분석 시작 시 로컬 색인을 한 번 준비한 뒤에는 각 GPT 검토 구간의 검색에서 색인 동기화를 반복하지 않는다. 검색은 준비된 인덱스를 재사용하고, 원고 변경 여부는 분석 시작 스냅샷과 최종 커밋 검사를 통해 별도로 감지한다. 이 분리를 통해 장편일수록 누적되는 불필요한 Chroma 점검 비용을 줄인다.

Chroma 조회가 일시적으로 실패하는 패키징 환경에서는 저장된 임베딩 벡터를 직접 읽어 로컬 순위를 계산한다. 이 경로가 가능하면 검색 요청마다 원고 전체를 다시 임베딩하지 않으며, 저장소까지 손상된 경우에만 원문 기반 폴백을 사용한다. 따라서 선택적 Chroma/ONNX 오류가 장편 분석의 CPU 사용량과 대기 시간을 전체 재임베딩 수준으로 악화시키지 않는다.

## 임베딩 모델 실측 참고

동일한 합성 검색 세트(152개 문단·40개 질의)의 실측은 모델 선택의 방향만 보여준다.

- Qwen3-Embedding 0.6B GGUF Q8: 파일 약 610MiB, 색인 397.44초, 질의 p50 561ms, Top-4 recall 80%.
- EmbeddingGemma 300M FP32 워커: warmup 6.97초, 색인 32.60초, Top-4 정답 질의 29/40(72.5%).

두 수치는 서로 다른 실행 경로와 합성 데이터의 결과이며 장편 처리 시간으로 직접 환산하지 않는다. 앱에서는 검색 품질을 우선하면 Qwen, 초기 색인 시간을 줄이면 Gemma를 선택할 수 있도록 모델별 한계와 측정 범위를 함께 표시한다.

### Qwen 실제 런타임 참고

같은 Mac에서 실제 Qwen3-Embedding-0.6B-Q8_0 GGUF를 10회·회차당 6,200자(총 62,000자·150청크)에 실행했다. warmup 1.253초를 제외한 색인은 106.921초(초당 1.403청크), 최대 RSS는 2,274.9MB였다. 이는 모델 파일 크기(약 639MB)와 별개인 실행 중 메모리·속도 측정이다. 100만 자로의 단순 선형 환산은 약 26.6분이지만 실제 장치·배치·캐시 상태에 따라 달라지는 참고치일 뿐 보장값이 아니다. 원본 결과는 `output/validation/realistic-manuscript-20260912/qwen-runtime.json`에 보존한다.

## 아직 남은 검증

- 실제 GPT 제공자에서 100회 원고를 끝까지 처리한 시간과 품질은 계정·네트워크 비용 때문에 자동 보장하지 않는다.
- Windows 실기기에서 같은 장편 원고의 메모리·CPU 사용량은 별도 측정해야 한다.
- 작품 전체 분석이 기본이며, GPT 패널에서 회차 범위를 지정해 분석할 수 있다. 범위 밖 기존 결과는 안전하게 병합·보존한다. 네이티브 앱에서 직접 조작하는 E2E와 실제 GPT 품질 측정은 별도 검증 대상이다.

### 100회 실제 Gemma 색인

실제 EmbeddingGemma 300M 워커로 100회·회차당 6,200자(총 620,000자·1,400청크)를 색인한 측정은 199.521초(초당 7.017청크)였다. 이는 테스트 제공자 오케스트레이션 시간이 아니라 해당 Mac의 로컬 CPU 색인 시간이다. 따라서 장편 첫 실행에서는 색인 준비만 약 3분 이상 걸릴 수 있으며, 앱은 진행률·예상 잔여 시간·취소를 제공해야 한다. 이후 회차 추가나 원고 수정에서는 변경된 청크만 색인하는 증분 경로를 사용한다.

## 재현 명령

provider stub으로 분량만 바꿔 오케스트레이션을 재현할 수 있다.

```bash
STORY_GUARD_BENCH_EPISODES=10 STORY_GUARD_BENCH_CHARS=50000 \
  PYTHONPATH=. .venv/bin/python scripts/validation/benchmark_long_episodes.py
```

이 명령은 실제 GPT 요청을 만들지 않으며, `long-episodes.json`에 청크 수·검토 창 수·증분 재사용·실패 격리 결과를 기록한다.

실제 EmbeddingGemma 워커로 10회·회차당 6,200자(총 62,000자·162청크)를 색인한 측정은 17.54초(초당 9.24청크)였다. 같은 워커로 10회·회차당 50,000자(총 500,000자·1,120청크)를 다시 측정한 결과는 158.775초(초당 7.054청크)였다. 초기 소규모 측정의 73.5MB는 호출 프로세스 RSS만 수집한 값이며, 격리 워커 자식까지 포함한 장편 재측정에서는 최대 RSS 약 1.66GB를 기록했다. 두 값 모두 해당 Mac의 한 번의 실행이며 모델 로딩·CPU 상태에 따라 변하고, GPT 응답 시간은 포함하지 않는다. 따라서 10회라는 편수만으로 실제 웹소설 장편 분량을 대표한다고 판단하지 않는다.

같은 50만 자 색인 뒤 11화(50,000자·112청크)를 추가한 증분 측정은 15.12초였다. 기존 1,120개 벡터는 재사용되고 신규 112개만 임베딩되었으므로, 수정·추가 시 전체 재색인을 피하는 경로가 실제로 작동함을 확인했다.

20화·회차당 50,000자(총 1,000,000자)도 측정했다. 2,240청크를 304.636초(약 5분 05초)에 색인했고, 21화 추가는 신규 112청크만 15.343초에 처리했다. 이 값은 해당 Mac에서의 Gemma 색인 시간이며 GPT 검토 시간은 포함하지 않는다.

CPU 부담을 확인하기 위해 `STORY_GUARD_EMBED_THREADS=2`로 20만 자를 별도 실행한 결과는 448청크·63.908초(초당 7.01청크)였다. 기본 4스레드 측정과 처리량 차이가 작아 기본값은 유지하고, 저사양 환경에서는 환경 변수로 2스레드까지 낮출 수 있다.
