# Story Guard: 3인 원격 AI 개발 협업 조사

조사일: 2026-09-09. 상태: 협업 방식 제안이며 팀원 배정, 코드 구조 변경, GitHub 규칙 적용은 아직 하지 않았습니다.

## 직접 권고

하나의 저장소에서 **공통 계약을 먼저 합의하고, 담당 영역별로 구현하며, 작은 PR을 매일 통합**하는 방식을 권합니다. 각 담당자는 다른 사람의 미완성 코드 대신 계약에 맞는 가짜 구현을 사용합니다. 실제 구현도 그 계약을 지키는지 자동 검사합니다.

목표는 종속성 0이 아니라 **구현 완료를 기다리는 시간과 변경의 파급 범위를 줄이는 것**입니다. 데이터 의미, 보안 경계, 사용자 경험처럼 함께 정해야 하는 결정은 남습니다. 처음부터 완전히 독립 개발한 뒤 마지막에 붙이는 방식은 이 결정을 뒤로 미룹니다.

아래 역할·주기·파일 배치는 이 프로젝트에 대한 제안입니다. 공식 문서에서 특정 3인 분담을 정답으로 보장하는 것은 아닙니다.

자료는 조사일에 확인했습니다. FastAPI의 SDK 문서는 OpenAPI 3.1 지원 도구를 안내합니다. 실제 저장소 버전과 호환되는 생성기·모킹 도구를 선택하고 버전을 고정해야 합니다. 이 조사는 새 패키지 도입이나 업그레이드를 확정하지 않습니다.

## 제안하는 3개 담당 영역

| 사람 | 책임 | 다른 구현을 기다리지 않는 개발 방법 |
|---|---|---|
| A: 제품 화면 | 공통 디자인, 원고·설정·검토·그래프 UI, 웹 소개·샘플 체험, 파일 선택·인증 화면 | 계약에 맞는 샘플 응답과 Mock API로 개발 |
| B: 분석 엔진 | 청킹, 로컬 임베딩·검색, 인물·관계·시간 추출, 근거 검증, LangGraph, 분석 평가 | 고정 원고·가짜 모델·저장소 인터페이스의 메모리 구현 사용 |
| C: 앱 기반·운영 | API, 영속 저장·마이그레이션, 작업 실행·취소, AI 인증·호출 어댑터, Tauri 패키징, 웹 체험 제한·배포 | 정해진 결과를 반환하는 가짜 분석 엔진으로 개발 |

A는 B의 실제 AI 분석을 기다리지 않습니다. B는 C의 완성된 DB나 OAuth를 기다리지 않습니다. C는 B의 분석 품질 개선이 끝나기를 기다리지 않습니다.

C의 범위가 가장 넓어질 가능성이 큽니다. 웹 소개·샘플 콘텐츠·제한 안내 화면은 A가, 모델 설치·호환성·자원 측정은 B가 맡고, 각자 자기 영역의 테스트도 작성합니다. C를 모든 테스트와 모든 PR 병합의 유일한 담당자로 만들지 않습니다. 순환 검토와 대체 검토자를 둡니다.

현재 경로 기준으로 A는 `src/components/`와 제품 화면, B는 `backend/app/pipeline/` 및 검색·모델 추론 서비스, C는 `main.py`·`repository.py`·`database.py`·`src-tauri/`·`desktopBackend.ts`가 중심입니다. `src/lib/api.ts`와 공통 타입은 생성·어댑터 경계를 정한 뒤 소유권을 고정합니다. `backend/app/services/` 전체를 B와 C가 동시에 소유하지 않고, 추론 구현은 B, 인증·제공자 연결 구현은 C로 파일을 구분합니다.

### 모듈 경계

```text
A: 화면 ── 앱 API 계약 ── C: API·저장·작업 관리
                                  │
                             분석 엔진 계약
                                  │
                         B: 검색·추출·검토
                                  │
                       모델 호출 / 자료 접근 인터페이스
                                  │
                  C: 실제 제공자 연결·저장 어댑터
```

계약을 분리하면 B는 구체적인 DB 테이블이나 OAuth 토큰을 알 필요가 없습니다. 엔진이 필요한 인터페이스는 B가 C와 합의해 정의하고, 실제 어댑터는 C가 구현합니다. 화면은 저장 DB나 모델을 직접 호출하지 않습니다.

데스크톱과 웹은 화면·분석 핵심을 공유하고, 파일 접근·인증·저장·사용량 제한을 환경별 어댑터로 분리합니다. 세 사람을 데스크톱·웹·AI로 각각 나누어 비슷한 화면과 데이터 구조를 두 번 만들지는 않습니다. 이를 위해 마이크로서비스 세 개나 별도 서버 세 개를 도입할 필요도 없습니다.

## 병렬 개발 전에 합의할 최소 계약

| 계약 | 최소 합의 내용 |
|---|---|
| 원고 자료 | 문서 ID·버전·회차·원문·정규화 규칙·삭제 상태 |
| 근거 | 문서 버전·구간 ID·시작/끝 위치·인용문, 위치 계산 단위 |
| 분석 입력·출력 | 실행 ID·입력 버전·스키마 버전·인물·관계·검토 후보·근거 |
| 분석 상태 | 대기·실행·완료·실패·취소·인증 필요·한도 중단 등의 의미와 전이 |
| 작가 교정 | 확정/구상, AI 해석 수정/의도된 전개, 수정 버전·충돌·재분석 시 보존 |
| 오류 | 인증 만료·한도 소진·모델 없음·메모리 부족·오래된 자료·유효하지 않은 근거 |
| 환경 기능 | 로컬 파일 선택 가능 여부, 직접 분석 가능 여부, 체험 분량 제한 |

원문 위치의 ‘문자 수’는 특히 명확히 해야 합니다. Python과 JavaScript가 동일한 문자열 위치를 다르게 계산하지 않도록 단위를 정하고, 이모지·조합 문자·줄바꿈이 포함된 공통 예제로 검증합니다. 처음에는 안정적인 구간 ID와 원문 인용을 중심으로 계약을 단순화할 수 있습니다.

HTTP 계약은 검토된 Pydantic 요청·응답 모델과 최소 라우트 선언을 원본으로 삼고, OpenAPI 스냅샷·TypeScript 타입을 생성하는 방식이 현재 FastAPI 구조에 자연스럽습니다. 실제 AI나 DB 없이 계약을 내보낼 수 있어야 합니다. 생성 파일을 세 사람이 각자 수정하지 않습니다. 비HTTP 엔진 입출력은 별도 버전 있는 모델로 정의합니다.

OpenAPI가 타입을 설명해도 ‘취소했는데 완료 결과가 게시되는가’, ‘재분석이 작가 교정을 지우는가’까지 자동으로 정하지는 않습니다. 이런 의미 규칙은 계약 예제와 동작 검사로 추가합니다.

### 계약 변경 절차

1. 영향받는 화면·엔진·저장 동작을 짧은 Issue로 기록합니다.
2. 담당자와 소비자가 계약·예제·실패 응답을 먼저 검토합니다.
3. 가능한 변경은 호환 가능한 추가로 나눕니다. 필드 추가도 엄격한 파서나 enum 처리에서는 깨질 수 있으므로 소비자 검사를 통과해야 합니다.
4. 형식·단위·상태 의미를 바꾸는 변경은 새 버전 또는 임시 호환 어댑터를 사용합니다.
5. 필요한 소비자가 전환한 뒤 구버전을 제거합니다. 해커톤에 필요 없는 장기 다중 버전 지원은 만들지 않습니다.

다른 사람의 코드까지 AI가 일괄 수정해 계약 변경을 숨기지 않습니다. 기존 계약으로 가능한 작업은 계속 진행하고, 계약에 의존하는 작은 부분만 조율합니다.

## 샘플 데이터가 세 사람의 공통 작업 재료가 되어야 함

동일한 가상 원고와 예상 구조를 버전 관리합니다. 예: 1화 사용 조건, 2화 계약 거절, 7화 검 사용. 이를 바탕으로 다음 사례를 함께 만듭니다.

- 근거가 명확한 충돌 후보와 예외 설정이 있는 정상 사례.
- 동명이인·별칭·소문·거짓말·회상·미회수 떡밥.
- 근거 문서 변경·삭제, 재분석 중 작가 수정, 오래된 결과 응답.
- 분석 중 취소, AI 인증 만료·한도 소진, 모델 미설치.
- 빈 작품·큰 그래프·긴 이름·작업 실패·체험 한도 도달.

UI는 이 자료로 전체 상태를 구현하고, API는 같은 계약 사례를 실제 핸들러로 검사합니다. 엔진은 사실 추출·근거 연결·시간 의미를 별도 평가합니다. Mock API나 가짜 모델의 성공을 실제 모델 품질 증거로 취급하지 않습니다.

MSW는 이 용도의 후보이며 필수 구매 서비스가 아닙니다. Pact의 소비자/제공자 양쪽 검증 원리를 참고하되, 3인 프로젝트의 첫 버전은 공통 fixtures·스키마 검사·실제 API 테스트로 시작할 수 있습니다. Pact Broker나 별도 계약 서버 도입은 필요성이 확인된 뒤 판단합니다.

## Git·통합 규칙

- 한 저장소, 각 사람은 자기 컴퓨터에 clone, 작은 작업마다 짧은 브랜치를 사용합니다. 개인별로 2~3주 유지하는 대형 브랜치는 만들지 않습니다.
- 한 사람이 여러 AI 작업을 동시에 실행하면 세션별 worktree를 사용합니다. worktree는 파일을 분리할 뿐 DB·포트·모델 캐시까지 분리하지는 않습니다.
- 작업별 임시 데이터 경로·포트·설정 파일을 분리하고 실제 작가 원고를 테스트에 사용하지 않습니다.
- 반나절~하루에 검토 가능한 PR을 목표로 하고, 진행 중 기능은 기본 비활성화 플래그 뒤에 통합합니다.
- 다른 팀원의 PR이 병합되면 자신의 변경과 함께 다시 검사합니다. 단순히 main을 매일 받기만 하고 자기 변경을 통합하지 않으면 상호 통합은 미뤄집니다.
- main은 필수 빌드·계약 검사와 다른 사람의 리뷰 후 병합합니다. 통합 기준 코드가 바뀌면 필요한 검사를 다시 실행합니다.
- root 설정·lockfile·DB 마이그레이션·계약은 좁은 전용 PR로 처리하고 담당자·검토자를 정합니다. 전체 포맷 변경을 기능 PR에 섞지 않습니다.
- CODEOWNERS는 수정 잠금이나 보안 경계가 아닙니다. 리뷰 담당 지정이며 필수 승인 규칙을 별도 설정해야 합니다.
- 보호 브랜치와 CODEOWNERS의 사용 범위는 GitHub 저장소 공개 여부·요금제에 따라 확인해야 합니다. 비용 때문에 규칙 강제가 불가능하면 수동 절차라는 한계를 명시합니다.

## AI에게 전달할 공통 기준과 작업 카드

기준 문서는 저장소에 함께 두고 PR로 갱신합니다. 각자의 채팅 기록은 팀의 공식 설계가 아닙니다. AI 도구별 지시 파일에서 동일한 공통 문서를 참조하도록 합니다.

| 제안 파일 | 내용 |
|---|---|
| `AGENTS.md` | 제품 범위, 변경 원칙, 실행·검사 명령, 공통 문서 위치 |
| `DESIGN.md` | 폰트·색·크기·공통 UI·데스크톱/체험판 차이 |
| `docs/architecture.md` | A/B/C 책임과 호출 방향, 공통 파일 담당 |
| `contracts/` | 생성된 API 스냅샷·엔진 계약·공통 예제 |
| `docs/decisions/` | 계약·스키마·공개 정책 변경의 짧은 결정 기록 |
| Issue / PR 템플릿 | 책임 범위, 완료 조건, 검증 근거, 후속 작업 |

이 파일들은 제안 목록이며 이번 조사에서 자동 생성하거나 시행하지 않았습니다.

AI 작업 지시 예:

```text
목표: 그래프 관계 선택 시 근거 패널을 표시한다.
계약: 합의된 Evidence / Relation 버전과 공통 샘플을 사용한다.
수정 범위: 지정된 그래프·근거 UI 파일과 관련 테스트.
공통 계약·DB·lockfile은 이 작업에서 변경하지 않는다.
완료 조건: 근거 여러 개, 삭제된 근거, 긴 인용문, 빈 상태를 표시한다.
검증: Mock API를 사용한 화면 검사와 관련 타입 검사를 수행한다.
계약이 부족하면 필요한 변경을 기록하고 기존 계약으로 가능한 부분을 진행한다.
다른 사람의 변경을 되돌리거나 자신의 성공에 맞춰 테스트를 약화하지 않는다.
결과 보고: 바뀐 동작, 실제 실행한 검사, 실패·미검증 범위를 적는다.
```

사람이 작업 카드의 완료 조건을 결정하고, AI가 만든 코드는 해당 사람이 이해·검증한 뒤 PR로 제출합니다. AI가 쓴 테스트만으로 사람이 검토해야 할 의미와 근거의 타당성을 대체하지 않습니다.

## 비용을 통제하는 검사 구성

| 실행 시점 | 검사 | 외부 AI |
|---|---|---|
| PR마다 | 타입·빌드·스키마/생성물 일치·Mock UI·실제 API+가짜 엔진 통합 | 호출하지 않음 |
| 엔진 변경 시 | 고정 원고로 근거 일치·관계 의미·캐시·교정 보존 검사 | 기본은 가짜 모델; 실제 품질은 별도 |
| 통합 시 | 화면→실제 API→실제 임시 저장→가짜 엔진→결과 표시 | 호출하지 않음 |
| 정해진 실증 시간 | 실제 임베딩, 사용자 AI 연결, 실제 모델 분석 품질·지연 | 승인된 계정·제한된 호출 |
| 배포 전 | 설치 파일, 최소 사양, 모델 다운로드, 인증·중단·삭제, 웹 제한 | 필요한 실제 경로 검증 |

PR마다 큰 모델을 내려받거나 GPT를 호출할 필요는 없습니다. 모델을 제외한 통합 검사는 협업 속도를 높이고, 실제 모델 검사는 정확도·호환성·자원 사용을 별도로 확인합니다. CI 러너·아티팩트·배포 서비스도 이용 한도와 보관 기간을 설정합니다. 무료 무제한을 가정하지 않습니다.

## 원격 진행과 초기 순서

첫 반나절~하루는 제안 시간입니다. 기존 결합도를 정리하는 데 더 걸리면 실제 작업량에 맞게 조정합니다.

1. 세 사람이 책임 경계·첫 사용자 흐름·핵심 계약·공통 예제를 합의합니다.
2. A는 샘플로 그래프·근거 화면, B는 가짜 모델로 엔진 입출력, C는 가짜 엔진으로 API·저장을 동시에 준비합니다.
3. 첫 1~2일 안에 ‘가상 원고 등록 → 분석 시작 → 완료 상태 → 그래프·근거 열람’의 통합 경로를 만듭니다. 이 시점의 가짜 분석은 개발 도구임을 표시합니다.
4. 이후 각자 독립 구현을 교체해 넣으며 작은 PR을 매일 통합합니다. 실제 임베딩·GPT·설치형 실행도 마지막 주까지 미루지 않습니다.
5. 매일 Issue에 완료 PR·다음 작업·계약 변경 요청·막힌 사항을 기록합니다. 짧은 리뷰 시간대를 합의하되, 항상 실시간 응답을 요구하지 않습니다.
6. 중대한 계약·원고 보관·공개 정책 결정은 문서로 남깁니다. 담당자가 부재해도 합의된 계약과 샘플로 계속 작업할 수 있어야 합니다.

## 이 조사에서 결정하지 않은 사항

- 실제 팀원별 역량·작업 가능 시간과 담당 배정.
- 지원 OS·최소 사양, 사용자 구독 연결의 실제 호환성.
- 모킹/코드 생성 도구의 구체 버전과 추가 의존성 도입.
- 현재 코드의 전체 재설계, 배포 실행, 유료 서비스 구매.

후속 구현의 우선 산출물은 **핵심 계약 + 공통 샘플 + 각 영역의 가짜 구현 + 통합 검사 한 경로**입니다. 모든 기능 명세를 완벽하게 작성할 때까지 병렬 작업을 미룰 필요는 없습니다.
