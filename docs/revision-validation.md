# 원고 누적·교체·재분석 검증

2026-09-10. 이번 작업은 디자인 변경이 아니라 원고 수명 주기와 파생 인덱스의 일관성을 검증한다.

## 구현

- 원고 화면의 `수정본으로 교체`: 문서 ID·회차·제목을 유지하고 내용과 청크를 트랜잭션으로 교체한다. 빈 파일과 누락 파일은 거절한다. 저장 중 오류가 발생하면 원고·기존 결과·이력이 함께 롤백된다.
- 추가·교체·삭제 시 이전 검토 후보, 작가 판단, 당시 원문을 별도 로컬 이력에 보관하고 오래된 현재 그래프를 비운다.
- GPT 재분석 성공 시 이력을 `동일 근거 재검출` / `이번 분석에서 미재검출`로 분류한다. 실패·취소 시 `재분석 대기`를 유지한다. 미재검출은 해소 확정이 아니다.
- 문서와 근거 텍스트가 동일한 후보에는 이전 작가 판단을 복원한다. 근거가 수정된 후보에는 이전 판단을 자동 이식하지 않는다. 의미적으로 같은 문제인지 판단하는 자동 매칭은 제공하지 않는다.
- 인덱스는 변경·추가 구간만 임베딩한다. 검색 전 원고와 동기화하여 제거된 구간을 반환하지 않는다. 임베딩 모델이 바뀌면 별도 인덱스를 사용한다.
- 관계 근거에서 해당 회차 원고를 열 수 있다.

## 실제 로컬 모델 평가

모델: Qwen3-Embedding-0.6B-Q8_0.gguf. 실제 llama.cpp 임베딩과 Chroma 검색을 사용했다. 합성 회차당 약 800자의 짧은 원고이며 실제 장편 회차 길이를 대표하지 않는다.

| 누적 회차/청크 | 이번에 임베딩한 청크 | 동기화 | 검색 평가 |
|---|---:|---:|---|
| 10 | 10 | 6.735초 | 1/1 근거 Hit@4 |
| 30 | 20 | 9.584초 | 4/4 근거 Hit@4 |
| 60 | 30 | 13.955초 | 4/4 근거 Hit@4 |
| 100 | 40 | 18.824초 | 4/4 근거 Hit@4 |

검색 시간: 60~88ms. 한 회차 교체 후 검색 125ms, 임베딩 1개 구간. 이전 청크 ID가 인덱스에서 사라지고 수정 원문이 검색됨을 확인했다. 삭제 후 해당 문서의 검색 결과·인덱스가 모두 제거됐고 재임베딩은 0개였다.

재현: `.venv/bin/python -m scripts.validate_revision_retrieval`
원시 결과: `output/validation/revision-retrieval/results.json`

## 자동 회귀 검증

원고 교체의 ID/회차 유지, 동일 파일 재교체의 무변경, 저장 실패 롤백, 빈 파일 거절, 이전 근거 보존, 작가 판단 복원, 재분석 실패 시 잘못된 해소 표시 방지, 증분 임베딩 및 삭제 인덱스 제거를 포함한다. GPT 응답을 고정한 자동 테스트는 저장·검증 로직을 검증하며 GPT 자체의 판단 정확도 측정이 아니다.

## 실제 GPT 평가의 경계

사용자 승인 후 GPT-6-Astra / Low로 실제 6회 요청을 실행했다. 캐시 재사용은 0회이며, 로컬 Qwen3 검색 → GPT 응답 → 인용 검증 → SQLite 저장 경로를 통과했다.

| 사례 | 기대 결과 | 실제 결과 | 전체 분석 시간 |
|---|---|---|---:|
| 미계약 상태로 봉인검 사용 | 충돌 후보 있음 | 후보 1개 | 49.98초 |
| 계약 체결 후 봉인검 사용 | 충돌 후보 없음 | 후보 0개 | 37.54초 |
| 충돌 원문에 시장·항구 설명 추가 | 충돌 후보 유지 | 후보 1개 | 50.63초 |

각 사례는 두 청크로 구성된 독립 작품이다. 세 번째 사례는 같은 구간에 무관한 문장을 붙였으며, 새 회차를 누적한 실험과는 다르다. 같은 작품을 교체하면서 GPT 재분석을 반복한 종단간 시험은 이번 6회에 포함하지 않았다. 원고 교체·이력 복원은 자동 회귀 시험으로 검증한 범위다.

모든 저장 관계·문제 후보의 근거 ID가 해당 작품의 원문에 속하는 것을 추가 확인했다. 작은 3개 사례의 통과를 전체 정확도 100%로 해석하지 않는다. GPT 응답에는 비결정성이 있어 반복 평가가 필요하다. 단 두 청크에 38~51초가 걸렸으므로 회차 증가에 따른 요청 수와 대기 시간은 아직 해결해야 할 제품 과제다.

원시 결과: `output/validation/revision-gpt/results.json`
재현 스크립트: `scripts/validate_revision_gpt.py` (재실행은 개인 계정 요청을 추가 사용하므로 이번 검증에서는 실행하지 않는다).

추가로 필요한 검증은 실제 길이의 한국어 원고, 별칭/동명이인, 장거리 떡밥, 부정·회상·시점 전환, 근거 누락에 대한 오탐/미탐 평가다. 현재 네 가지 검색 문항의 성공률을 서비스 전체 정확도로 일반화하면 안 된다.


## 동일 작품의 실제 수정·복원 검증 (후속 실행)

개인 계정 GPT-6-Astra / Low, 실패 1회 포함 총 6회 추가 요청. 이전 실제 충돌 분석 DB를 복제하여 동일 작품 ID로 수행했다. 사용 중인 작품은 변경하지 않았다.

| 단계 | 결과 | 소요 |
|---|---|---:|
| 기존 충돌에 판단 보류 지정, 무관한 3화 추가 후 분석 | 첫 응답이 90초 한도를 초과하여 실패. 판단 이력은 deferred/pending 유지 | 응답 한도 초과 |
| 2화를 계약 체결 후 검 사용으로 교체하고 재분석 | 후보 0개, 수정 전 청크 제거, 이력의 판단 보류 유지 및 미재검출 표시 | 54.83초 / 3회 요청 |
| 같은 수정본을 다시 분석 | 후보 0개 유지, GPT 요청 0회, 캐시 3개 재사용 | 0.25초 |
| 무관한 3화를 제거하고 2화를 원래 충돌로 복원 | 후보 1개 재탐지, 새 청크 ID에도 기존 판단 보류 복원 | 56.22초 / 2회 요청 |

처음 실패한 누적 분석을 통과로 간주하지 않는다. 수정본 재분석은 성공했지만 최초 실패와 원고가 같지 않으므로 동일 요청의 재시도 성공으로 보지도 않는다. 마지막 단계는 3화 삭제와 2화 복원을 함께 수행한 시험이다.

검증에서 드러난 다음 과제는 단일 GPT 응답의 90초 시간 초과와 구간 단위 복구다. 무조건 자동 재요청하면 사용량을 늘리므로 실패 위치·완료 구간·캐시 사용 가능 상태를 사용자에게 보여주고, 사용자가 재개할 수 있도록 해야 한다. 이번에는 응답 시간 제한이나 제품 분석 코드를 임의로 바꾸지 않았다.

결과 파일: `output/validation/revision-sequence/results.json`. 실행 스크립트는 `scripts/validate_revision_sequence.py`, 실패 후 범위 내 후속 스크립트는 `scripts/validate_revision_recovery.py`, `scripts/validate_revision_restore.py`다. 후속 스크립트는 누적 요청 수를 검사하고 명시적인 실행 플래그를 요구한다.
